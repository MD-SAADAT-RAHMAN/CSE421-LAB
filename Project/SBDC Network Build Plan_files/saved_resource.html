01

Design decisions taken before anyone opens Packet Tracer

Five judgement calls are baked into everything below. Read them first — two of them are the difference between a working failover demo and one that quietly refuses to fail over.

1. The PHD–TMA serial link is deliberately kept out of RIP

The spec asks for a direct PHD–TMA link (§2.1.3f) and for the failure of the SCCC–TMA path to reroute traffic through TMA → DCS → ERU → SCCC (§2.6.2). Those two clauses fight each other: if RIP runs over the PHD–TMA serial, then when TMA loses the central switch it simply learns everything from PHD at AD 120, the AD 130 floating static never installs, and the required failover path is never taken.

The fix is to build the cable, address both ends, keep it pingable — and mark it passive-interface in RIP on both routers. The subnet is still advertised to everyone else; no routing information crosses that link. The physical redundancy the spec asked for exists, and the failover path stays deterministic.

2. Every router-to-router link except the central segment is serial

Only SCCC–ERU is required to be serial (§2.1.3c), but making ERU–DCS, DCS–TMA, DCS–ESC and PHD–TMA serial too buys something concrete: the DCS router is required to use directly connected static routes (§2.5.3b) — exit-interface-only, no next hop. On an Ethernet link that form is broken by design (the router ARPs for every remote destination and leans on proxy ARP). On a point-to-point serial it is exactly correct. All six routers become 2811s with WIC-1T / WIC-2T modules.

3. SCCC redistributes its statics into RIP

§2.5.2 says SCCC runs both dynamic and static routing and must know every network. That is only half the job — TMA and PHD are RIP-only and would never learn the ERU / DCS / ESC side. redistribute static metric 5 under router rip on SCCC is what makes §2.6.1 ("TMA reaches all external networks through SCCC") true.

4. ERU reaches TMA's LAN via DCS, not via SCCC

ERU is static-only and cannot detect a failure three hops away. If ERU pointed at SCCC for 11.8.5.0/24, then during failover SCCC would forward TMA-bound traffic to ERU and ERU would send it straight back — a two-router loop. Pointing ERU at DCS for TMA's LAN is correct in both states, so no loop can form. The path is mildly asymmetric during normal operation; pings and TCP are unaffected.

5. RIP timers are tuned down

When TMA's central-switch port is shut, TMA purges its RIP routes instantly (interface down) and the floating statics install immediately — that half of the demo is fast. The return path is not: SCCC's own port stays up (PHD is still on that switch), so SCCC must wait out the default 180 s invalid + 240 s flush timers before its floating static to TMA installs. timers basic 10 30 30 40 on all three RIP routers turns a four-minute wait into about forty seconds. Set it identically on SCCC, TMA and PHD or the protocol destabilises.

Servers stay inside department LANs

§2.4.6c says to subnet server networks "if separated". Keeping DNS, web, mail and DHCP servers on their department LAN with static addresses from the top of the range satisfies §2.4.7, keeps the VLSM table readable, and removes six subnets and six router sub-interfaces of work. Every server address is documented in §04 as if it were its own allocation.

Interface & hardware map

All six routers are Cisco 2811 — two on-board FastEthernet ports plus two WIC slots. Serial ports only appear after a WIC module is fitted, and modules can only be fitted with the device powered off.

Do this before any cabling

In Packet Tracer: click the router → Physical tab → click the power switch to turn it off → drag the WIC module into an empty slot → power back on. Adding a module to a running router silently fails, and the serial interfaces never appear in the CLI.

The three static route forms, and which one goes where

Next-hop

ip route net mask 11.8.7.137
Names the neighbour's IP only. Used on R-ERU and R-SCCC.

Directly connected

ip route net mask Serial0/1/0
Names the exit interface only. Valid on point-to-point serial. Used on R-DCS.

Fully specified

ip route net mask Se0/1/0 11.8.7.141
Both together. Explicitly forbidden on R-DCS by §2.5.3b(ii) — do not use it anywhere.

How the failover works

A floating static is just a static route with a manually raised administrative distance. RIP has AD 120; the backup statics are configured at AD 130, so while RIP is advertising a prefix the static stays out of the routing table entirely. Shut TMA's Fa0/1 and every RIP route TMA learned through that interface is purged at once — the AD 130 statics drop into the table in the same second.

Loop check

The design is loop-free in both states because two routers never point at each other for the same prefix:

  • TMA → SCCC LAN, after failure. TMA sends to 11.8.7.145 (DCS). DCS routes 11.8.0.0/23 out Se0/1/0 to ERU. ERU routes 11.8.0.0/23 to 11.8.7.137 (SCCC). Delivered in three hops, exactly the path §2.6.2 demands.
  • SCCC → TMA LAN, after failure. The RIP entry is gone, so SCCC's AD 130 static sends to 11.8.7.138 (ERU). ERU's static for 11.8.5.0/24 points at DCS, not back at SCCC — this is decision 4 in §01, and it is the single thing preventing a ping-pong loop. DCS delivers over Se0/0/0.
  • PHD → TMA LAN, after failure. PHD relearns 11.8.5.0/24 from SCCC, because SCCC's newly active floating static is picked up by redistribute static. Traffic goes PHD → SCCC → ERU → DCS → TMA. The idle PHD–TMA serial is not used, as intended.

How the ESC relay actually resolves

R-ESC receives the broadcast on Fa0/0, stamps giaddr = 11.8.6.1, and unicasts it to 11.8.2.250. The DCS server matches giaddr against its pools' gateway fields, finds ESC-POOL, and offers from 11.8.6.10 upward. Two things must be true for the reply to come back: the DCS server's own Default Gateway must be set to 11.8.2.1, and R-DCS must hold the static route for 11.8.6.0/24 out Serial0/0/1. Both are already in this plan — but a missing default gateway on the server device is the usual reason this silently fails.

Failover demonstration

Run this as a scripted sequence and screenshot every numbered step. It is the deliverable most likely to be examined closely, and it is worth rehearsing once before capturing.

Step 1 — baseline, before touching anything

! on R-TMA
show ip route
! expect: R  11.8.0.0/23 [120/1] via 11.8.7.129, FastEthernet0/1
!         R  11.8.2.0/23 [120/6] via 11.8.7.129   (redistributed, metric 5+1)
! there must be NO 'S' route to those prefixes yet

show ip route 11.8.0.0
show ip protocols

! on TMA-PC1 command prompt
tracert 11.8.1.251
! expect 2 hops: 11.8.5.1 -> 11.8.7.129 -> 11.8.1.251

Step 2 — break the primary path

! on R-TMA
configure terminal
interface FastEthernet0/1
 shutdown
end

Deleting the cable between R-TMA and SW-CENTRAL in the workspace works equally well and looks more convincing in a screenshot. Either is acceptable; be consistent between the demo and the report.

Step 3 — prove the floating static installed

! on R-TMA, immediately
show ip route
! expect: S  11.8.0.0/23 [130/0] via 11.8.7.145
!         S  11.8.2.0/23 [130/0] via 11.8.7.145
! the AD in brackets flipping 120 -> 130 IS the evidence. Screenshot this.

show ip route static
Wait about 40 seconds before testing end-to-end

TMA switches over instantly, but SCCC's return route to 11.8.5.0/24 is a RIP entry that has to age out first. With timers basic 10 30 30 40 that takes roughly 30–40 s. Pings during that window will fail — that is expected, not a bug. If you skipped the timer tuning, use Packet Tracer's Fast Forward Time button (each press advances 30 s) until show ip route on R-SCCC shows S 11.8.5.0/24 [130/0] via 11.8.7.138.

Step 4 — prove the traffic really takes TMA → DCS → ERU → SCCC

! on TMA-PC1 command prompt
tracert 11.8.1.251

! expected hops, and this is the money shot for spec 2.6.2:
!   1   11.8.5.1     R-TMA   (LAN gateway)
!   2   11.8.7.145   R-DCS   (arrived on Se0/0/0)
!   3   11.8.7.141   R-ERU   (arrived on Se0/0/1)
!   4   11.8.7.137   R-SCCC  (arrived on Se0/0/0)
!   5   11.8.1.251   destination

ping 11.8.1.251
ping www.smartcity.gov.bd
! and confirm the website still loads in Desktop -> Web Browser

Step 5 — restore and confirm reconvergence

! on R-TMA
configure terminal
interface FastEthernet0/1
 no shutdown
end
! wait ~20 s, then
show ip route
! the 'S ... [130/0]' entries must be replaced by 'R ... [120/x]' again
! the floating statics are still in running-config, just dormant

Include the before/after show ip route pair side by side in the report. The single most persuasive piece of evidence is the same prefix appearing first as [120/1] and then as [130/0].

After Phase 1 — Track A's address table has to be signed off by B and C before anyone types an IP, because every later task depends on it.
